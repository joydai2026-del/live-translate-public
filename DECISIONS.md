# Decisions

## Inline QR encoder, no dependency
QR codes are generated by `src/qr.js`, a small inline encoder (byte mode, ECL M) derived from Project Nayuki's MIT-licensed QR Code generator. The copyright and permission notice are kept in the file header. This keeps the server at zero runtime dependencies. `checks/review-R1.test.js` compares the matrices with a reference encoder.

## Abuse limit defaults (T3, REVIEW-R1 M1/M2)
Token buckets per client IP, in memory, with idle entries swept so the maps stay bounded:
- `POST /api/rooms`: burst 10, refill 10 per hour.
- Final lines across all rooms: burst 30, refill 1 per second.
- Room-not-found answers: burst 30, refill 0.5 per second, then 429.

Per room, interim and final lines use separate buckets (interims burst 20 at 5/s, finals burst 20 at 2/s), so interim traffic can never starve finals. Stored text per room is capped at `MAX_ROOM_CHARS` = 200,000 characters (409 after). The daily translation budget (`TRANSLATE_DAILY_CHAR_LIMIT`) is unlimited by default.

The client IP is `req.socket.remoteAddress`; `X-Forwarded-For` and `X-Forwarded-Proto` are honoured only with `TRUST_PROXY=1`.

These values are starting points for local and small deployments. Values for a public deploy are still open (see docs/internal/tasks/T3-review-R1.md, Needs owner).

## Client send queue (T3, changed in T4 and T3-review-R2)
Finals are posted with `wait: false`: the server answers once the line is stored and broadcast, and the translation arrives on the event stream as the same-id update. So no POST stays open for a slow provider, and Chrome's 6 connections per origin on plain-http LAN are never used up by finals; interims never wait behind them. The next final goes out when the previous one has landed: its POST was answered, or the page's own event stream shows it, matched by its `clientId` (never by text, so an older identical line such as "OK", or a backlog replay, cannot release the queue). A final in flight or in backoff holds back the ones after it, so ids keep the spoken order.

Each final gets a random 32-hex-char `clientId` (`crypto.getRandomValues`, which also works on plain http) and keeps it on every retry. The server keeps a per-room map keyed by speaker and clientId and answers a repeat with the stored line, without storing, translating, broadcasting or spending rate-limit tokens again, also while the first POST is still translating. So a final whose response was lost (network switch, proxy timeout) is stored once and keeps its first id.

Retries: 429, 5xx and network errors, with backoff (0.5, 1, 2, 4, 8 s, then every 8 s, up to 20 tries). A 403 on a guest page drops the saved guest token and asks for a new one once per POST (the host may have reset guests). Interims are throttled to one every 350 ms (about 3 per second, latest text wins) and never overtake their final. An exact repeat of one of the last few finals within 3 s is skipped (Android Chrome repeats finals). Host and guest pages share the same queue code.

## Original first, translation as an update (T4, G1)
A final is stored (transcript and backlog) the moment it arrives, with `pending: true`, and translated in the background, so lines translate concurrently. Grace window: 150 ms. A translation ready within it is broadcast once, so fast providers look exactly as before. A slower one is broadcast at once as pending (the original only) and again with the same id when done, or with `error` and `errorKind`. 150 ms (the brief allows up to 250) leaves room inside the 500 ms "original on the guest screen" target for the client head start, the network and rendering. SSE ids are a per-room broadcast counter rather than the line id, so a reconnect with Last-Event-ID also receives lines that were updated while the reader was away.

## LAN join address (T4, G2)
Only `node src/server.js` reads `os.networkInterfaces()` (once, at startup) and passes the result to `createServer({lanHost})`; in-process servers keep using the request's Host. Order: first non-internal IPv4 in 192.168/16, then 10/8, then 172.16/12. 172.16/12 comes last because Docker and WSL bridges live there. Public addresses are never used. The LAN address replaces the Host only when the Host is localhost, 127.x or [::1], keeping the Host's port. `PUBLIC_URL` always wins.

## Guest replies (T4, G3)
`POST /api/rooms/:code/guests` hands out a random 24-byte token (base64url), kept in the guest tab's sessionStorage. At most 20 per room and 30 per client IP per hour; tokens are compared in constant time. A guest may only send the room's other language (`zh` in `en-zh`, `en` in `zh-en`, either in `both`), so a guest token cannot pose as the host's side of a one-way room. Lines carry `speaker: 'host' | 'guest'`. Typing works on plain http; hold-to-speak shows only where SpeechRecognition exists and the page is a secure context.

## Presence (T4, G7, changed in T3-review-R2)
`event: presence` {readers} counts the room's open streams except the host page's own, which it opens as `?role=host&token=<hostToken>` (also on reconnect). The token is checked with `room.checkToken`; `?role=host` with a missing or wrong token counts as a reader, so a silent eavesdropper shows up in the host's count. Presence goes to every stream on each connect and whenever the count changes. The guest page uses the presence event that follows its backlog as the "caught up" marker, so read-aloud never speaks the backlog.

## Stream caps (T3-review-R2, M4)
`MAX_STREAMS_PER_IP = 20` open event streams per client IP (across all rooms, `clientIp`, so TRUST_PROXY applies) and `MAX_STREAMS_PER_ROOM = 50`. Above either the request gets 429 JSON with `retry-after`, before any SSE headers. A slot is freed once, on whichever comes first of the request or response closing or finishing (client left, room ended, server closed). The authenticated host stream is exempt from both, so the host always gets its stream. 20 per IP leaves room for a family or a classroom behind one NAT reading several rooms; 50 per room is far above an in-person conversation.

## Global stored text (T3-review-R2, m12)
`MAX_TOTAL_CHARS = 50,000,000` characters of stored final text across all rooms (`new RoomStore({maxTotalChars})`), on top of the 200,000 per room. A final over it gets 503; the per-room 409 is checked first. Ending, deleting or expiring a room frees its characters. 50M characters is about 100 to 200 MB of strings, which fits a small server.

## On-device translation (T4, G5 spike)
A final POST with a valid host token may carry `translation` (string, at most 4000 chars). The server stores and broadcasts it and does not call the translator or count it against the daily budget. With a guest token the field is ignored and the server translates, so a guest cannot show the host an invented translation. The host page uses Chrome's `Translator` API only when `Translator.availability()` reports `'available'` for the pair (model already on the device), creates the translator on a user gesture (mic tap, push-to-talk press, typed send), and falls back to the server on any failure or after 5 s. It never triggers a model download. Trust: a host could send any text as the translation; that is the same trust the host already has over the original text.

## Daily budget refunds (T3-review-R2, m1)
The budget is reserved before the provider call. A failed call (any error kind except `budget`, which never called the provider) gives the characters back, but only to the UTC day it was reserved in, so a call that fails just after midnight does not inflate the new day.

## Transcript token (T4, G8, enforced since T3-review-R2)
`POST /api/rooms` returns a `readToken` and the host download links carry the host token. `GET /transcript` answers 403 unless `?token=` is one of the two (`room.checkReadToken`). Unknown rooms still answer 404 first. Guests get no token and no download (whether they should, for example via the QR fragment, is open for the owner).

## Guest reset (T3-review-R2, m4)
`POST /guests` always requires `content-type: application/json`, also with no body, so a cross-site form cannot mint guest tokens. `DELETE /guests` `{hostToken}` revokes every guest token and frees the 20 slots; the host page has a "Reset guests" button with a confirm. A guest page that gets 403 drops its saved token and asks for a new one, so guests who are still there keep replying.

## Markdown transcript escaping (T3-review-R2, m10)
In the md transcript, text and translations escape backslashes and backticks, turn `<` and `>` into `&lt;` and `&gt;`, and break up `![` and `](`. Plain `[` and `]` stay, so "[zh]..." lines read as before (checks/acceptance.test.js relies on that). json and txt stay verbatim.
